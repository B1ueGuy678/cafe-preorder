## 0. 为什么需要阶段 3

阶段 2 交付的是一条**顺利路径**上完整的产品：状态机、下料时刻、队列排序、模拟支付全部可用，
39 项自动化测试（smoke 20 + e2e 19）覆盖了这些逻辑。

但一家真实咖啡店开门后的前十分钟，遇到的不是顺利路径，而是：

- 顾客手机在地铁口信号只剩一格 → 请求发不出去 / 回不来
- 顾客以为没点成功，又点了一次「确认并支付」 → 两张单、两杯咖啡
- 两个店员同时看到同一单，同时点「接单」
- 支付环节没成功，页面却显示下了单
- 顾客拿手机站在店门口，屏幕 375px 宽

阶段 3 只做一件事：**把正常路径之外的窟窿补住**。不新增产品功能、不改产品定位。

## 2. 关键解释：什么叫「并发抢同一杯」

**本产品没有库存计数**（阶段 1 非目标里明确没做库存），所以不存在「两个顾客抢最后一杯」。

真实的并发冲突全部发生在**同一张订单被两个操作同时修改**：

1. 两个店员同时点「接单」
2. 顾客点「取消」的同时，店员点了「接单」
3. 顾客端轮询触发的「超时自动取消」与店员「接单」同时发生

这三件事的形状是一样的：**先读状态 → 判断能不能流转 → 再写状态**。
两步之间只要有别的请求插进来，两个请求就都会认为自己合法，后写的覆盖先写的。

**修法**：把状态流转改成**带状态条件的原子更新**

```ts
// 之前：读 → 判断 → 写（中间有窗口）
const order = await prisma.order.findUnique({ where: { id } });
assertTransition(order.status, to);
await prisma.order.update({ where: { id }, data: { status: to } });

// 之后：让数据库来判胜负
await prisma.order.updateMany({
  where: { id, status: from },   // 状态必须还是我读到的那个
  data: { status: to },
});
// count === 0 → 别人先改了 → 409，让前端刷新
```

这条改动落在 `src/lib/domain.ts` 的 `transition()`，**所有状态流转共用它**，
所以一处修好，接单/拒单/做好/取餐/取消/超时全部受益。

## 3. 任务分解

### S3-1 服务端硬化（异常路径）

| 项 | 内容 | 验收标准 |
| --- | --- | --- |
| R-1 | 状态流转原子化 | 3 个并发「接单」请求，**恰好 1 个 200**，其余 409；订单终态唯一 |
| R-2 | 重复提交幂等 | 同一个 `clientToken` 提交两次，两次都返回**同一个订单 id**，库里只有一张单 |
| R-3 | 畸形请求体 | `Content-Type: application/json` 但 body 不是 JSON / 不是对象 → **400**，不再是 500 |
| R-4 | 支付失败分支 | `PAY_MODE=MOCK_FAIL` 时下单返回 **402**，且**不产生任何订单行** |
| R-5 | 口令门限速 | 连续 5 次错误口令后，第 6 次返回 **429**；正确口令在限速窗口外仍可登录 |

**验证**：

```bash
node ./node_modules/typescript/bin/tsc --noEmit
node scripts/smoke.mjs
node scripts/e2e.mjs        # 需 dev server 运行中
node scripts/guards.mjs     # 自带一个配了口令 + 支付失败的独立 server
```

### S3-2 顾客端韧性

| 项 | 内容 | 验收标准 |
| --- | --- | --- |
| R-6 | 轮询失败可见 | 断网后 4 秒内出现「网络不稳，正在重试」横幅；恢复后横幅消失并显示最后更新时间 |
| R-7 | 写操作失败可读 | 断网时点「取消订单」，提示中文且**不是** `Failed to fetch`；按钮可重试 |
| R-8 | 空态 | 菜单为空 / 无可选到店时刻时，页面给出明确说明而不是空白卡片 |
| R-9 | 提交中防重 | 提交按钮在请求期间禁用，且带 `aria-busy`；重复点击不产生第二张单（与 R-2 双保险） |

**S3-2 的机器核对方式**（不新增脚本，而是扩展现有可核对的面）：

- 订单页服务端渲染必须出现「状态每 4 秒自动刷新」与「取消订单」
- 把菜单整体下架后请求 `/`，HTML 必须出现「店家还没有上架饮品」与按钮文案「暂无可下单的饮品」
- 断网横幅不该出现在首屏 HTML（初始在线）；出现即说明状态初始化写错了

### S3-3 店员端韧性

| 项 | 内容 | 验收标准 |
| --- | --- | --- |
| R-10 | 队列陈旧可见 | 轮询失败时队列顶部出现「队列可能已过期」横幅、底部改为「网络恢复后队列会自动刷新」；恢复后显示「已同步 · 最后更新 HH:MM:SS」 |
| R-11 | 操作失败回执 | 接单/拒单失败时给出明确原因（409 说明「已被其他人处理」并自动刷新队列） |
| R-12 | 空队列 | 无待接单时显示「当前没有待接单」而非空表格 |

**S3-3 的机器核对方式**：

- `/staff` 首屏 HTML 必须含「正在同步…」与三处空态文案，且**不含**「队列可能已过期」

- R-11 的并发回执需要两个标签页同时对同一单操作，步骤见 §6

## 5. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| e2e 依赖外部 dev server，环境不稳时结果不可信 | 中 | 测试脚本自带清理；`guards.mjs` 自带 server 与端口，跑完即杀 |
| 两个 `next dev` 共用 `.next` 会互相覆盖构建产物（实测症状：另一个 server 的页面开始 404/500） | 高 | `guards.mjs` 启动前检查 3000 端口，占用即拒绝运行（exit 2），不做静默并行 |
| 限速用进程内存计数，重启即失效 | 低 | 单店单实例场景够用；多实例部署时改为存储层计数（阶段 6 评估） |
| 幂等只覆盖「同一次会话的重试」 | 低 | token 由前端生成并随重试保留；换页面重下单本来就是新意图 |

## 6. 人工验证清单（机器跑不了的部分）

下面这些必须真人在浏览器里做一遍（连同 `PRODUCT.md` 的 AC-1 / AC-11 / AC-13 / AC-15）：

**R-6 断网可见**

1. 先下一单，停在 `/order/:id`
2. DevTools → Network → 把限速切成 **Offline**
3. 期望：**下一次轮询（4 秒内）**出现「网络不稳 · 正在重试…」横幅；页面保留旧状态但明确说明它可能过期
4. 切回 **Online** → 期望：横幅消失，底部变为「已同步 · 最后更新 HH:MM:SS」

**R-7 写操作失败可读**

1. 仍在 Offline 状态点「取消订单」
2. 期望：toast 是中文「网络连接不上，请检查网络后重试（操作可能没有生效）」，
   **不是** `Failed to fetch`；按钮恢复后可再点
3. 恢复网络后再点一次取消 → 期望取消成功，且**不会**变成两张单（R-2 的幂等键兜底）

**R-10 店员端陈旧可见**

1. 打开 `/staff`（本机没配 `STAFF_PASSCODE` 时直接进入）
2. DevTools → Network → **Offline**
3. 期望：4 秒内出现「队列可能已过期」横幅，底部变成「网络恢复后队列会自动刷新」
4. 切回 **Online** → 期望：横幅消失，显示「已同步 · 最后更新 HH:MM:SS」

**R-11 并发处理回执（单人也做得了）**

1. 开两个 `/staff` 标签页，都停在待接单队列
2. 在 A 里对某一单点「接单」，再在 B 里对**同一单**点「接单」
3. 期望：B 显示「这一单刚被其他人处理过，队列已刷新」，队列立即刷新；
   不会出现两杯咖啡都开始做的情况（服务端只允许一个流转成功）

**R-14 窄屏 375px**

1. DevTools 设备工具栏选 iPhone SE（375×667）
2. 走完：选饮品 → 选到店时间 → 填尾号 → 下单一单 → 看订单页
3. 期望：全程无横向滚动，底部按钮不被遮挡、不被键盘顶掉
